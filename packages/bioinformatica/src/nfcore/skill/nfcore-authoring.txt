# Authoring nf-core modules, subworkflows, and pipelines

This is the frame for helping a scientist create new nf-core components or adapt existing
ones. The rule that governs all of it: **orchestrate nf-core's own scaffolding,
never hand-roll it.**

## Conformance is defined by the specification
The official nf-core specification is the **source of truth** for every conformance
question — module/subworkflow structure, naming, testing, formatting, and pipeline
requirements vs. recommendations: https://nf-co.re/docs/specifications/overview (and its
child pages). Ground answers in it, not in memory; when unsure what "conformant" means,
read the relevant spec page or scaffold-and-lint rather than guessing. For reference, the
spec requires a module to have `main.nf` (with a `stub` block, and it MUST report tool
versions), `meta.yml`, `environment.yml` (Conda deps), and an nf-test test that includes a
stub test — but treat the live spec, not this summary, as authoritative.

## The non-negotiable principle
nf-core defines that structure — the module/pipeline layout, the template, the config and
metadata conventions, the linting rules. It is generated by the official tools, not by you:
- New module → `nf-core modules create`
- New subworkflow → `nf-core subworkflows create`
- New pipeline → `nf-core pipelines create`
Run these through the shell tool (with approval — they write files). **Do not write the
boilerplate by hand** and do not invent a parallel layout: a hand-made skeleton that
drifts from the current template is worse than no skeleton, because it will fail lint and
mislead the scientist about what nf-core expects.

**And never reimplement the science.** A module *wraps an existing, validated tool*; it
does not contain a novel algorithm you wrote. Helping wire a tool into nf-core's
conventions is in scope; writing a new aligner, caller, or statistical method is not
. If a scientist wants genuinely new analysis logic, that belongs in the tool the
module wraps, authored and validated on its own terms — not smuggled into a module body.

## The workflow
1. **Check the toolchain first.** Authoring needs `nf-core` (the Python CLI) and `nf-test`.
   Use the environment tool to check; if either is missing, guide installation the same
   way as any other dependency (self-install where allowed, otherwise show the exact
   command) before scaffolding — do not proceed as if they were present.
2. **Scaffold** with the appropriate `nf-core … create` command; show it first.
3. **Fill in the scientist's actual content** — the tool invocation, its inputs/outputs,
   the `meta.yml` documentation — inside the generated files, keeping to the structure.
4. **Test and lint.** A component is not done until `nf-test` passes for it and
   `nf-core modules lint` / `nf-core lint` is clean. Treat lint findings as the definition
   of "conformant", and fix them rather than suppressing them.

## Honesty
The template and lint rules move over releases; rely on what the installed tools actually
generate and report, not on a remembered layout. If you are unsure what the current
template produces, scaffold it and read it rather than guessing.
